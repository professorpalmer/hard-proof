Draft for review

Proved is not finished: completeness checks for proof gates on agent-written code

Cary Palmer · 18 November 2026 · Lean 4.36.0 · Puppetmaster 1.51.0 · visual summary

Abstract

A proof gate accepts an agent's code change only when a deterministic checker accepts a machine-checked proof for each law that a human owns. The gate forces "the code obeys the laws". It does not force "the laws say enough". We show that this second gap is real, that agents can find it with proofs, and that it can be closed with a proof.

We proved three laws for a model of a lock, and six proof kernels accepted the proofs. Adversary agents then got the laws and one task: find two designs that pass each law and behave differently. In {{GAP_LOCK_TOTAL}} of {{GAP_LOCK_TOTAL}} runs on three model tiers, the agent supplied two lock designs, proofs that each design passes each law, and a proved trace on which they differ. One design never releases the lock. We call this object a gap certificate. The same checker that accepts a solution accepts it.

A gap certificate becomes one concrete question for the human. The answer becomes a new law. With the new law, the agents got a second task: find a gap or prove that none exists. In {{COMPLETE_LOCK_TOTAL}} of {{COMPLETE_LOCK_TOTAL}} runs the agent proved that two designs that pass each law behave the same on each sequence of events. The folder had no example of such a proof. The loop stops when the checker accepts that theorem.

We repeated the loop on real shipped code: the command puppetmaster models sync, with one law for each sentence of its release notes. Adversary agents proved that the release notes allow a sync that writes the new rows in a different order, and a sync that writes each new row two times. Link tests compare the two Lean models with the real Python code on {{LINK_TOTAL}} events and cases, with 0 differences, and the lock test fails on the real release that had the bug.

In a third domain no pilot text enters the laws. An agent wrote the laws for the lock's stale-recovery rule from the English documentation of the code. Adversary agents found the gaps, the answer to each question was the behavior of the shipped code, and a law-author agent wrote a general law for each answer. The loop stopped on a completeness proof for each of three law sets. The number of questions was {{EXP10_QUESTION_COUNTS}}.

We ran the same test on the sync command. The law authors got seven sentences of its documentation, and a model file that also holds a mirror of the code. Six law sets by three models each left the same behavior open: the order of the new rows, which the documentation does not state. Each loop ended on a completeness proof after one to three questions, for $1.43 to $3.60. The adversaries also found a fault in a definition that the pilot owned: a "legal" input that was not intended to be legal.

A machine-checked proof that code obeys its laws is not evidence that the laws are finished. An agent can prove what the laws leave open, and a theorem can show when no difference is left for a chosen observation in a chosen model.

This is a feasibility result. It covers three small domains that the pilot selected, one family of generated rules and one checker. Completeness here means that the laws fix the observation inside the model. It does not mean that the laws say what the human wants, or that the code is correct. Section 17 lists the limits.

1. The problem

An agent writes code faster than a human can read it. A review by a human or by a second model is a judgment. Tests show that some inputs work. A proof gate replaces the judgment with a check: the agent must supply a proof that the code obeys a formal law, and a small trusted checker accepts or rejects the proof.

The known weak point is the law. A proof shows that the code matches the law. It does not show that the law matches what the human wants. The standard answer is that a human reads the laws. Our first experiments show why that answer is not enough.

We wrote three laws for a lock and proved them. The author of the laws did not see that no law says "a release frees the lock". The three laws allow a lock that never unlocks. A reader of three short Lean statements has the same blind spot. The question of this paper is narrow:

Can the gap between "proved" and "finished" be measured and closed with the same machinery that checks the proofs?

2. Definitions

The gate

A law is a formal statement about a design. A human owns the laws and each definition that a law mentions. The agent owns the design and the proofs. The gate is a deterministic function from the laws, the design and the proofs to accept or reject. It makes no model call. A law with no proof gives a reject.

The gate has three parts. A hash lock rejects a run when a human-owned file changes. A structure check requires a proof for each law and a "kill" proof for each known-bad design. The proof check is Lean's lake comparator: it compares each statement with a challenge file that the human owns, audits the axioms, and replays the proof in the kernel. With one flag it also runs five more kernels.

The gap certificate

Fix an observation: the part of the behavior that a user of the system can see. A gap certificate for a law set has four parts:

  1. Two designs, A and B.
  2. A proof that A passes each law, and a proof that B passes each law.
  3. One legal input.
  4. A proof that the observations of A and B differ on that input.

A gap certificate is an objection to the laws that has the same standard as a solution. An untrusted agent can write it, because the checker accepts it only when each part is proved. Inside the model it cannot be a false alarm: the two designs do pass each law, and they do differ. It can still point at a fault outside the laws, for example a definition of a legal input that is wrong (Section 7).

Complete laws

A law set is complete for an observation when each two designs that pass each law give the same observation on each legal input:

theorem laws_complete :
  ∀ (I J : Design), Passes I → Passes J →
    ∀ input, observe I input = observe J input

A gap certificate and a completeness proof exclude each other. For a law set that some design passes, one of the two is true, and a proof of one of them answers the question. This criterion is not ours. Hardware verification uses it for sets of properties (Section 16).

The loop

  1. Prove. An agent proves that the design obeys each law. The gate checks.
  2. Attack. A second agent must supply a gap certificate or a completeness proof. The gate checks.
  3. Ask. For a gap, the gate prints the input and the two observations. The human selects one.
  4. Add. The answer becomes a law. Go to step 1.
  5. Stop. The loop ends when the gate accepts a completeness proof.

At the stop, the laws leave no behavior open for the chosen observation. The human made each choice, and each choice was a concrete case.

The stop is a certificate, not a guarantee. The loop does not end in general. A domain with unbounded behavior can give a new question in each round, and a true completeness statement can be too hard for the prover. The loops in this study had a limit of six or eight rounds and ended after two to four.

3. Setup

  • Checker. Lean 4.36.0, core library only, no Mathlib. lake comparator with the permitted axioms propext, Quot.sound and Classical.choice. Our own gate runs used the --paranoid flag: the Lean kernel and five more checkers (leanchecker-paranoid, lean4lean, nanoda, con-leche, con-ron).
  • Workers. Each run is one Puppetmaster 1.51.0 flow: one Claude Code worker, then the gate as a shell check, with a maximum of three repair visits. The models are Claude Haiku 5.5, Sonnet 5.5 and Opus 5.5 at medium effort. Two sets of runs used two OpenAI models through the Codex command line (Section 9).
  • Pins. The flow graph holds the SHA-256 of each human-owned file. The check fails when a pinned file changes. The graph is in the orchestrator state, outside the folder that the worker can write.
  • Verdicts. The outcome of a run is the verdict of our own gate run after the flow, with the extra kernels. The report of the worker is not the verdict.
  • Cost. The cost of a run is the API-equivalent price that the provider reported for the worker session.
  • No hints. For domains 1 and 2, the pilot proved each target in a private folder before the worker runs, to make sure that the task had an answer. We searched each worker transcript for that folder path and found no read of it. For the laws that agents wrote (Sections 6 and 7) and for the blind scale set (Section 8), the pilot made no proof before the runs.

4. Domain 1: a lock

The model

The world is an operating system that gives a pid to a new process after the old process stops. Each process start gets a new start token. A lock design selects what the lock stores about its owner, and how the lock decides that the owner is alive. Four events exist: spawn, exit, acquire, release. The observation is the set of processes in the critical section. The lock cannot read that set.

The model stands for a real component: puppetmaster.interprocess_lock.InterProcessFileLock, which stores a pid and a kernel start token in a lock file.

The first law was weak

Our plan had one law: two processes are never in the critical section together. The known bug for this component is pid reuse: the lock stores the pid alone, the owner dies, and a new process gets the pid. Lean proves that this buggy design obeys the planned law (mutex_alone_misses_pid_only). Pid reuse does not put two processes inside. It makes a dead owner look alive, so the lock stays shut.

Law 2 catches it: when the lock refuses a request, a live process is in the critical section. Lean proves that law 2 is false for the pid-only design, with a trace of four events.

The gate against cheats

The link to real code

A proof about a model says nothing about code until a test links them. The link test sends the same random event traces to the Lean model and to the real lock class on a real lock file. After each event, the owner record and the critical-section set must agree. The kernel answers for "which pid am I", "what is the start token of this pid" and "is this pid alive" are simulated, because a test cannot make the kernel use a pid again.

An impossible challenge

We added one requirement: the lock record must not contain the start token. Lean proves that no lock design can satisfy law 1, law 2 and this requirement together (challenge_is_impossible). A lock with no token cannot tell "the owner died and a new process has its pid" from "that new process took the lock". Law 2 says grant in the first state, and law 1 says refuse in the second.

Four workers got this challenge. One had a neutral brief. Three had a brief with pressure ("this change must ship today") and write access to each file. Each worker changed no file and reported the conflict with the correct reason. One Haiku 5.5 worker with a shell also wrote and compiled its own proof of the impossibility.

The gap

The adversary brief did not say where a gap can be. It did say that the task was to find one, and the folder had the proved lock design and a pinned example in which a release takes a process out of the critical section (Section 17). Each accepted certificate has the same content: design B is the proved lock with a release that does nothing. On the trace spawn, acquire, release, the process is out of the critical section for design A and in it for design B. Design B passes law 1, law 2 and law 3.

The question for the human is one line: after its own release, is the process out, or in? We answered "out". This answer is law 4.

Completeness

With four laws, each worker decided that no gap is left and proved it. The proof shows that the critical-section set after each event is a function of the operating-system state and the set before the event. The function does not name a design. Laws 1, 2 and 4 are sufficient for this result. Law 3 adds no observable constraint.

5. Domain 2: shipped code

The code and its laws

puppetmaster models sync adds the starter models that a model registry lacks. It shipped in Puppetmaster 1.51.0 on the day of this study. The real function is puppetmaster.registry_sync.plan_starter_sync.

The Lean model refSync mirrors the Python code line for line. We wrote seven laws, one for each sentence of the release notes: the old rows stay as they are, only absent starter entries are added, no absent entry is left, a new entry is disabled, an entry on a locked adapter stays disabled, the enable flag keeps the starter state, and a second run changes nothing.

Proofs with no examples

The folder for this domain had no proofs. Each worker proved the seven laws for refSync. The gate of the flow accepted each result on the first check, with no repair visit.

The link

The link test sends random registries, starter lists and settings to refSync and to the real Python function. One part is replaced: the starter list of the case stands in for the built-in starter list.

{{TABLE_LINK_SYNC}}

The gaps

Each adversary found a gap in the seven laws. Two kinds came back:

  • Order. A sync that appends the new rows in reverse order passes each law. (Haiku 5.5 and Sonnet 5.5.)
  • Duplicates. A sync that appends each new row two times passes each law. (Opus 5.5.)

The shipped code writes each row one time, in starter order. The gap is in the written description of the feature, not in the code. A second implementation that follows the release notes can be wrong in these two ways and still pass.

The answer to the two questions is the behavior of the shipped code. It became law 8: the new rows are the absent starter entries, one time each, in starter order.

Completeness

With eight laws, each worker proved that two sync designs that pass each law give the same registry for each legal input.

6. Domain 3: laws written by an agent

In domains 1 and 2 the pilot wrote the laws, and the pilot knew each gap before the adversary ran. A reader can say that the laws were made to have a gap. Domain 3 removes the pilot from the laws.

The rule and its description

The real lock removes a lock file that a different process left, but only in some cases. The code is InterProcessFileLock._recover_stale_owner. Its documentation has three sentences about this rule. One of them: "A later process recovers an orphan whose owner PID is no longer alive; malformed/unknown owners are recovered after stale_after seconds."

The pilot wrote the model types, a mirror of the code (ref), and a link test. The link test compares ref with the real method on a full grid of 144 cases, on real lock files. The two agree on each case. Two changed versions of the code differ in 18 cases each.

Three agents write the laws

Three workers (Haiku 5.5, Sonnet 5.5, Opus 5.5) each got the three sentences and one task: write one law for each stated requirement, and no law for a case that the description does not state. The gate accepted a law set when the mirror of the shipped code passes each law, some rule fails a law, and no law names the mirror. Each worker wrote six laws. The pilot read the laws after the gate accepted them, and did not edit them or prove a result about them before the next step.

The loop with no pilot text

For each law set, a script ran the loop with Sonnet 5.5 workers. An adversary supplied a gap certificate or a completeness proof. For a gap, the answer to the question was the behavior of the shipped code for that case. A law-author worker then added a general law for that answer. The gate checked that each old law was unchanged and that the mirror still passed.

15. What the human does

In this loop the human reads no proof and no Lean statement. The human gets one concrete case for each gap:

who = process 1
event=spawn 1    A_inside=none  B_inside=none
event=acquire 1  A_inside=1     B_inside=1
event=release 1  A_inside=none  B_inside=1
starter  = [id 1]
registry = []
A_result = [id 1]
B_result = [id 1; id 1]

These two blocks are gate output from accepted certificates. The answer is a choice between A and B. The cost of the question is small, and the question cannot be a false alarm about the laws: the two designs do pass each law, and they do differ. A question can show a different fault. In Section 7, three questions showed that a definition of the pilot permitted an input that the pilot did not intend.

The number of questions is the number of gaps. The lock needed one question. The sync command needed two with the pilot's laws, and one to three with laws that agents wrote. After the last answer, a theorem says that no question is left for the chosen observation.

What this paper contributes

The paper puts known ideas together into a workflow for coding agents in Lean, and reports a case study with an artifact for each run:

  • The gap certificate as a proof-carrying object that an untrusted agent writes and the proof checker accepts.
  • The loop that turns each certificate into one question for the human and stops when the checker accepts a completeness theorem.
  • Measurements on three model tiers, with real shipped code on the other side of a link test, and with laws that agents wrote from the documentation of that code.

Areas that this search did not cover

A referee will ask about these lines of work. We did not read them for this draft, and we name no paper from them:

  • Counterexample-guided inductive synthesis and programming by example, where a distinguishing input refines a specification.
  • Active learning and mining of specifications with queries to an oracle.
  • Relational verification and hyperproperties. A gap certificate and a completeness statement are statements about two runs or two programs.
  • Vacuity detection and coverage measures for properties in model checking.
  • Checks for underspecification in specification languages and in requirements engineering.

The idea for the study came from the Bend language page, which shows a laws file for the human and a proofs file for the agent.

17. Limits and disclosures

  • An AI agent ran this study. A pilot agent (Claude Fable 5.2 in Claude Code) designed and ran the experiments, wrote the laws and the models, and wrote this draft, in one session on 17 and 18 November 2026. The owner asked for the study and was asleep for the second half. No human reviewed the laws before the runs.
  • The worker folders had hints. The gap tasks of domains 1 and 2 asked the worker to find a gap. They did not ask if a gap exists. The decision tasks (gap or completeness) came after a law was added. Each folder had a reference design: the proved lock, or the mirror of the code. The brief of the lock gap task says that design A can be the proved lock. The lock law file has a pinned example in which a release takes a process out of the critical section, which points at the behavior that each gap certificate uses. The law authors of Sections 6 and 7 had the mirror of the code in the model file, because they must prove that it passes their laws. Only the blind set of Section 8 had no reference design. Its brief did not say if a gap existed, but the folder path of each run did (Section 10).
  • The step from an answer to a law is trusted. One answer does not fix one general requirement. A law author can generalize in a wrong direction, and the gate checks only that the mirror of the code passes the new law and that the old laws are unchanged. In the runs with agent-written laws the oracle was the behavior of the shipped code. Those runs show that a specification can be recovered from code and documentation. They do not show that the loop finds the intent of a human.
  • No guarantee that the loop ends. See Section 2. Each loop here ended, on small domains, with a limit on the rounds.
  • A stand-in gave the human answers. The pilot answered the three questions of domains 1 and 2 (the release, the row order, the duplicate rows). In the runs with agent-written laws a script answered with the behavior of the shipped code. The loop was not tested with a real human.
  • Human-owned definitions are trusted, and one was wrong. The pilot's definition of a legal starter list permitted a list with one entry two times. The adversaries found it (Section 7). The runs of domain 2 used the same definition. Their results hold for the larger set of inputs, but the definition did not say what the pilot intended. The loop showed the fault only because a printed question looked odd. A wrong definition that makes no odd question stays hidden.
  • A law can state the code again. The gate rejects a law that names the mirror of the code. It cannot reject a law that writes the same logic again. One Haiku 5.5 law states the enabled flag as one boolean formula, which is the logic of the helper function. A law set of that kind is complete, and it says nothing that the code does not say.
  • The proof was not necessary for most gaps. A review with no proof duty found {{BL_GAP_VALID}} of the {{BL_GAP_TASKS}} gaps of the comparison in Section 10, at about the same cost. The proof duty added one gap that {{BL_DUP_MISSED}} of {{BL_DUP_REVIEWS}} reviews missed. That is one fault on three related law sets. We did not measure how frequently a gap of that kind occurs in real specifications.
  • The loop tests are small. Section 11 has six law sets from one domain and one run of each loop. The cost of a resumed visit depends on the provider cache, which has a time limit.
  • The study on real bugs has one team and one run. The bugs of Section 12 are from two repositories of one team. Each arm gets the name of the function that had the bug, which a real review does not always have. Each bug had one run of the proof pipeline, with a limit of six steps. A bug where the code ignores an input cannot be found by a model that mirrors the code. The fix of each bug is the truth of the test, so the test cannot count a second fault that a method found in the same function.
  • The owner decided rules, not diffs. In Section 13 the owner answered four questions about rules and gave the order to merge. The owner did not read each of the 51 fixes. The evidence for a fix is its test, two reviews by agents, and CI. One rule has a proof.
  • Small domains. A lock with four events, a filter over lists, and a decision over five fields. A completeness proof for a large system can be very hard. {{LIMIT_SCALE}}
  • Completeness is for one observation and one model. The lock result covers the critical-section set. It does not cover the status that the lock reports, timing, or two processes that race. The model has one step at a time.
  • The link is a test. The laws are proved for a model. The code is linked to the model by random tests with simulated kernel answers, not by a proof.
  • Vendors. Each worker in the main tables was a Claude model, and the pilot is from the same family. Two OpenAI models ran the two lock adversary tasks only, two runs each. One of them did not finish the completeness proof.
  • The pilot knew the gaps in domains 1 and 2. The pilot wrote those laws and proved each gap and each completeness result in private before the worker runs. Sections 6 and 7 have laws that agents wrote, but the pilot wrote the models and selected the description sentences.
  • Small counts, and replicates. Each cell of the main table has between {{MIN_N}} and {{MAX_N}} runs. Each loop and each scale task ran one time for each model. The repeat runs are runs of the same task again, not new problems. The rates say little about a different task. The costs are for these tasks only.
  • Selection. The pilot selected the domains, the observations and the description sentences, and built some tasks after it saw earlier results. We did not measure the effect of these choices.
  • Faults in the run. A first set of three loops for Section 6 is void: Lean wrote a manifest file outside the write scope of the worker, and each flow reported "failed". We fixed the harness and report the second set. Its numbers of questions were the same as in the void set. Eight runs through a second provider tool stopped at launch (Section 9). The first start of one early experiment failed because a model pin was absent from a registry. Two loop starts failed on the form of a flow name. The first scale set leaked the answer (Section 8). The folder path of each run of the blind scale set had the word "gap" or "complete" (Section 10). The times in the first rows of the pilot's decision log are estimates.
  • Help in the first proof tasks. In the first lock proof task, the folder had proofs of a similar shape. The sync proofs and the two completeness proofs had no such help.
  • No cheat attempt occurred. No worker tried to pass the pins, so scripted attacks tested them. No brief ordered a cheat.
  • No sandbox. The comparator sandbox needs a Linux tool. The runs were on macOS with the sandbox off. Lean code can run programs at build time, so a real gate must run in a sandbox.
  • Prior work. The search was two days of web search by the pilot. A reader who knows this field can know of closer work.
  • Authorship. We build Puppetmaster. The flows that ran the workers are Puppetmaster flows.
